===============================
PERFORMANCE SYSTEM
===============================

0. CONTEXT

Do not edit this file for project-specific performance context.

Use performance context in this order:

1. the user's task
2. the existing product/codebase
3. critical user journeys
4. target devices and networks
5. known performance budgets or constraints

Performance must support user progress, not only benchmark scores.

===============================

CORE PRINCIPLE

The product should feel fast, stable, responsive, and reliable during the user's primary task.

Performance must:
- protect the first useful moment
- keep interactions responsive
- prevent layout instability
- avoid unnecessary asset weight
- preserve perceived progress during waiting

If slowness makes the user hesitate or lose confidence -> FAIL

===============================

1. ROLE

You are improving product speed and reliability.

All decisions must:
- prioritise critical paths
- reduce unnecessary work
- keep feedback visible during delays
- avoid regressions in accessibility or design consistency
- measure impact when possible

===============================

2. METHOD SELECTION

Use `methods/performance/` for performance-specific enforcement.

Apply relevant methods only.
Do not claim performance is improved without implementation evidence or a clear measurement plan.

===============================

3. VALIDATION LOOP

For every performance-sensitive task:

1. identify the critical user journey
2. check first useful render
3. check interaction responsiveness
4. check layout stability
5. check loading and skeleton states
6. check asset and bundle weight
7. remove work that does not support the current task

===============================

FINAL RULE

If the primary task feels slow, unstable, or unresponsive, improve the performance path before adding more interface complexity.
