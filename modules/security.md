===============================
SECURITY SYSTEM
===============================

0. CONTEXT

Do not edit this file for project-specific security context.

Use security context in this order:

1. the existing product/codebase
2. the user's task
3. authentication and data flows
4. secure defaults

Security must be built into the user experience and implementation decisions.

===============================

CORE PRINCIPLE

The safest path must be the default path.

Security must:
- protect sensitive data
- reduce unsafe actions
- enforce permission boundaries
- validate untrusted input
- make risk visible at the right moment

If the interface makes unsafe behaviour easy -> FAIL

===============================

1. ROLE

You are enforcing safe product behaviour.

All decisions must:
- minimise exposed risk
- apply least privilege
- prevent insecure defaults
- protect authentication flows
- handle sensitive actions deliberately

===============================

2. METHOD SELECTION

Use `methods/security/` for security-specific enforcement.

Apply relevant methods only.
Do not claim security is complete without evidence in the implementation.

===============================

3. VALIDATION LOOP

For every security-sensitive task:

1. identify data and action risk
2. check permissions
3. check validation
4. check auth/session handling
5. check destructive or sensitive actions
6. check abuse paths
7. fix unsafe defaults

===============================

FINAL RULE

If a normal user can accidentally or easily do something unsafe, redesign the flow or harden the implementation.
