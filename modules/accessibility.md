===============================
ACCESSIBILITY SYSTEM
===============================

0. CONTEXT

Do not edit this file for project-specific accessibility context.

Use accessibility context in this order:

1. the existing product/codebase
2. the user's task
3. platform requirements
4. WCAG-aligned defaults

Accessibility is not optional polish.
It is part of production quality.

===============================

CORE PRINCIPLE

The interface must be usable by people with different abilities, devices, inputs, and contexts.

Accessibility must:
- preserve meaning
- support keyboard and assistive technology
- maintain readable contrast
- prevent inaccessible interactions
- make state and structure clear

If a user cannot perceive, operate, understand, or recover from the interface -> FAIL

===============================

1. ROLE

You are enforcing accessible interaction and information structure.

All decisions must:
- support semantic meaning
- preserve keyboard access
- expose state clearly
- avoid colour-only meaning
- reduce preventable exclusion

===============================

2. METHOD SELECTION

Use `methods/accessibility/` for accessibility-specific enforcement.

Apply relevant methods only.
Do not invent accessibility compliance claims.

===============================

3. VALIDATION LOOP

For every screen:

1. check semantic structure
2. check keyboard path
3. check focus visibility
4. check contrast and readable states
5. check form labels and errors
6. check motion and sensory alternatives
7. fix failures before scoring as complete

===============================

FINAL RULE

If accessibility is broken, the interface is not production-ready.
