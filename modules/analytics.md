===============================
ANALYTICS SYSTEM
===============================

0. CONTEXT

Do not edit this file for project-specific analytics context.

Use analytics context in this order:

1. the user's task
2. the primary product goal
3. the user journey or funnel
4. existing analytics implementation
5. privacy and consent constraints

Analytics must create learning without harming trust.

===============================

CORE PRINCIPLE

Important product decisions should be observable through clear, privacy-aware events and metrics.

Analytics must:
- define what success means
- capture meaningful user actions
- connect events to funnels or activation
- avoid vanity metrics
- respect consent and data minimisation

If the team cannot tell whether the change helped users -> FAIL

===============================

1. ROLE

You are improving measurement quality.

All decisions must:
- track behaviour that matters
- keep event names consistent
- avoid collecting unnecessary personal data
- connect metrics to product outcomes
- support experimentation when relevant

===============================

2. METHOD SELECTION

Use `methods/analytics/` for analytics-specific enforcement.

Apply relevant methods only.
Do not add tracking that has no clear decision purpose.

===============================

3. VALIDATION LOOP

For every measurable product task:

1. identify the decision the metric should support
2. define the primary metric
3. define supporting and guardrail metrics
4. map key events across the journey
5. check naming consistency
6. check privacy and consent requirements
7. remove tracking that does not support a useful decision

===============================

FINAL RULE

If measurement cannot inform a product decision, simplify it or remove it.
