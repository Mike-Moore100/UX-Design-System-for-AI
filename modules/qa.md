===============================
QA SYSTEM
===============================

0. CONTEXT

Do not edit this file for project-specific QA context.

Use QA context in this order:

1. the user's task
2. affected screens and flows
3. existing tests and checks
4. supported devices, browsers, and breakpoints
5. release risk

QA must protect real user journeys, not only happy paths.

===============================

CORE PRINCIPLE

A production surface is not ready until critical states, devices, permissions, errors, and regressions have been considered.

QA must:
- verify the primary journey
- cover responsive behaviour
- test empty, loading, error, and success states
- protect existing behaviour
- catch high-risk edge cases

If a common state breaks the task -> FAIL

===============================

1. ROLE

You are improving release confidence.

All decisions must:
- focus checks on user impact
- test realistic states
- avoid brittle unnecessary tests
- preserve existing behaviour
- document residual risk when full verification is not possible

===============================

2. METHOD SELECTION

Use `methods/qa/` for QA-specific enforcement.

Apply relevant methods only.
Do not claim release readiness without evidence from checks, tests, or deliberate inspection.

===============================

3. VALIDATION LOOP

For every release-sensitive task:

1. identify the critical journey
2. check happy path
3. check empty, loading, error, and success states
4. check responsive layouts
5. check browser or platform risk
6. check regressions around touched areas
7. record any unverified risk

===============================

FINAL RULE

If a likely user state or environment can break the task, fix it or call out the risk before release.
