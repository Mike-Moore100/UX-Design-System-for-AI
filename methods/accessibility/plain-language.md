# Plain Language

## What
Plain Language makes interface content easy to understand for users with different reading levels, language backgrounds, and cognitive contexts.

Simple language improves access.

## Why it matters
Complex wording creates barriers even when the interface is visually accessible.

Plain language:
- improves comprehension
- reduces mistakes
- supports cognitive accessibility
- helps non-native speakers
- speeds task completion

Clear words are an accessibility feature.

## When to apply
- forms
- errors
- legal or billing moments
- onboarding
- settings
- instructions
- help content

## How to apply

- use common words
- put important information first
- keep sentences short
- explain unavoidable technical terms
- avoid idioms and vague phrases
- write actions in direct language

The user should understand what to do without rereading.

## Implementation rules

- error messages must explain the fix
- CTAs must use predictable action language
- instructions must be in task order
- technical terms need explanation where users may not know them
- avoid humour in critical messages
- do not hide important meaning in long paragraphs

## Example

Bad:
- "Authentication failed due to invalid credentials"
- "Leverage advanced configuration"
- "Proceed with operation"

Good:
- "Email or password is wrong"
- "Choose your settings"
- "Delete project"
- "You can change this later"

## Fail conditions

- user must interpret jargon
- critical instructions are too long
- error copy is vague
- CTA language is abstract
- wording assumes expert knowledge unnecessarily

## Enforcement rule

If language slows understanding, rewrite it in plain, direct words.
