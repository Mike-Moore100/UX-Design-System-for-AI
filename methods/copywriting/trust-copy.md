# Trust Copy

## What
Trust Copy communicates safety, credibility, reliability, and accountability at moments where users need confidence.

Trust copy must be specific enough to be believed.

## Why it matters
Users hesitate when they are unsure whether a product is safe, legitimate, or reliable.

Strong trust copy:
- reduces perceived risk
- supports sensitive actions
- improves conversion quality
- strengthens brand credibility
- prevents support confusion

Generic trust language can feel empty.

## When to apply
- signup
- checkout
- security pages
- enterprise pages
- data collection
- permissions prompts
- billing
- destructive actions

## How to apply

- identify the trust concern in the moment
- state what is protected, guaranteed, or controlled
- include specific evidence where possible
- explain data use plainly
- make policies and support paths accessible
- avoid broad claims without proof

The user should know what they can rely on and why.

## Implementation rules

- trust claims must be accurate
- privacy and security copy must be specific
- guarantees must define scope
- proof must be close to high-risk actions
- policy links must not replace essential in-context explanation
- avoid unverifiable phrases like "100% secure"

## Example

Bad:
- "Your data is safe with us"
- "Trusted by thousands" without context
- asks for OAuth permissions without explanation
- hides refund details behind legal pages

Good:
- "We only request read access to import your project list"
- "SOC 2 report available on request"
- "Cancel from billing settings any time"
- "Used by 2,400 product teams"

## Fail conditions

- user cannot tell what is protected
- trust claim is vague
- evidence is absent
- sensitive permission is unexplained
- policy is used as a substitute for clear copy

## Enforcement rule

If trust copy makes a claim the interface cannot support with specifics or proof, rewrite it or remove it.
